# Mneme 全时域记忆引擎 - 产品需求文档

## **版本**：v0.2**日期**：2026-04-24**状态**：待评审**负责人**：王雅心**参与角色**：产品经理、解决方案架构师、飞书集成开发工程师、分析师

## 一、需求概述

### 1.1 产品定位

**一句话定位**：企业级主动记忆伙伴 —— 不等用户开口，主动记住团队交流中的关键信息，在遗忘临界点主动提醒。**核心价值**：

* 异步从飞书对话中抽取关键记忆，无需用户主动记录

* 基于艾宾浩斯遗忘曲线，在记忆即将遗忘时主动推送复习提醒

* 时序敏感，自动覆写冲突信息，确保团队始终引用最新决策

* 支持工作流打断后的上下文快速恢复**与传统笔记工具的本质区别**：

| 维度   | 传统笔记（如 Notion/飞书文档） | Mneme         |
| ---- | ------------------- | ------------- |
| 记忆触发 | 用户主动记录              | 系统自动抽取 + 用户补充 |
| 检索方式 | 用户主动回忆关键词           | 遗忘临界点主动推送     |
| 信息更新 | 手动覆盖或标注"已过时"        | 时序敏感自动覆写      |
| 遗忘处理 | 信息静默消失，用户无感知        | 主动复习提醒，干预遗忘曲线 |

***

### 1.2 痛点分析（核心章节）

#### 痛点一：关键信息消失在对话流中 🔴 高痛点

```plain&#x20;text
场景还原：
- 周会讨论时，张三提到"API密钥下周过期，需要更新"
- 团队成员点头表示知道了
- 两周后密钥过期，故障告警，排查半天发现"诶当时谁说的来着？"
- 结果：生产事故 + 加班修复 + 可能的经济损失


```

## **根因**：团队对话中有大量有价值的信息，但这些信息随着对话流被遗忘，没有主动干预机制。

#### 痛点二：信息更迭后仍沿用旧版本 🔴 高痛点

```plain&#x20;text
场景还原：
- 4月1日：团队决定"周报发送给 A 同学"
- 4月15日：团队决定"周报改发送给 B 同学"（飞书消息）
- 5月1日：某人发周报给 A，理由是"我一直都是发给 A 的"
- 结果：尴尬 + 重复劳动 + 对 A/B 的不尊重


```

## **根因**：旧信息没有"失效标记"，新信息没有"权威声明"，用户依赖"脑子记"。

#### 痛点三：心流被打断后难以恢复 🟠 中高痛点

```plain&#x20;text
场景还原：
- 你正在专注开发功能 F，忽然群里有人问："那个 API 对接的事谁负责？"
- 你切换过去回答了问题（2分钟）
- 切回来后，发现刚才想到的"这个接口要传 user_id 而不是 open_id"被遗忘了
- 结果：可能引入了隐藏 bug，或者回头再花时间回忆


```

## **根因**：人的工作记忆容量有限，被打断后上下文切换频繁，导致"刚才想做什么"被静默遗忘。

#### 痛点四：新人进来一切从头学 🟡 中痛点

```plain&#x20;text
场景还原：
- 新来的同学问："我们项目的发布流程是什么？"
- 老人回答："哦这个，我翻翻之前的消息... 你等会儿"
- 花了 20 分钟翻聊天记录


```

## **根因**：团队知识散落在历史对话中，无法快速提取和检索。

#### 痛点量化评估

| 痛点               | 频率        | 严重度         | 可解决的提升空间 |
| ---------------- | --------- | ----------- | -------- |
| 关键信息消失在对话流       | 高（每周多次）   | 高（可能导致事故）   | ★★★★★    |
| 信息更迭后沿用旧版本       | 中（每月几次）   | 高（造成返工）     | ★★★★☆    |
| 心流打断后难以恢复        | 高（每天多次）   | 中高（影响效率/质量） | ★★★★☆    |
| 新人 onboarding 困难 | 低（入职时才发生） | 中（影响效率）     | ★★★☆☆    |

## 四、功能模块

### 4.1 功能一：智能记忆抽取

#### 4.1.1 功能概述

从飞书对话流中自动识别并抽取值得记忆的关键信息，无需用户主动声明"帮我记住这个"。

#### 4.1.2 触发条件

| 类别    | 关键词/模式                             | 示例                    |
| ----- | ---------------------------------- | --------------------- |
| 决策声明  | "决定是..."、"改用..."、"更新为..."          | "我们决定用 PostgresDB"    |
| 截止时间  | "截止..."、"deadline是..."、"需要在...前完成" | "这个需求周五前上线"           |
| 负责人变更 | "转给..."、"交接给..."、"A 负责 → B 负责"     | "发布流程转给 C 同学"         |
| 配置/密钥 | 含"密钥"、"密码"、"token"、"API"、"配置"      | "API Key 是 sk-xxx"    |
| 外部承诺  | "我们已经..."、"向客户承诺..."               | "我们承诺周三前交付"           |
| 竞品/市场 | "竞品更新了..."、"对方说..."                | "对方说他们的 Q2 会发布 AI 功能" |
| 心流相关  | "等下要..."、"回头要..."、"稍后处理..."        | "等下记得发周报"             |

#### 4.1.3 记忆类型定义

| type       | 说明    | 示例                    |
| ---------- | ----- | --------------------- |
| `decision` | 团队决策  | "决定用 MongoDB 存用户数据"   |
| `fact`     | 事实性信息 | "API 密钥是 sk-prod-xxx" |
| `intent`   | 意图/待办 | "等下要发周报给 A"           |
| `command`  | 指令性内容 | "以后周报发给 B"            |

#### 4.1.4 业务规则

* BR-001-01：抽取阈值可配置，默认 0.7（置信度低于此值不存储）

* BR-001-02：同一对话窗口内，5 分钟内的连续讨论视为同一话题

* BR-001-03：抽取结果需可溯源，存储原始消息 ID 和 context\_snapshot

* BR-001-04：context\_snapshot 用于心流恢复场景

#### 4.1.5 验收标准（Given-When-Then）

* **Given** 用户在群聊中发送"我们决定用 MongoDB 存用户数据"，**When** 系统处理该消息，**Then** 生成记忆，type="decision"，content 包含 "MongoDB" 和 "用户数据"

* **Given** 用户发送普通闲聊"今天天气真好"，**When** 系统检测，**Then** 不生成记忆（置信度 < 阈值）

* **Given** 系统抽取了一条记忆，**When** 存储完成，**Then** 同时记录 source\_message\_id 和 context\_snapshot

### 4.2 功能二：遗忘曲线主动复习（L1 + L2）

#### 4.2.1 功能概述

基于艾宾浩斯遗忘曲线，通过两种机制触发推送：

* **L1 衰减预警**：定时扫描 strength 低于阈值的记忆，触发复习提醒

* **L2 相似上下文**：当对话内容与某条记忆的 context\_snapshot 语义相似度 > 0.75 时，触发关联提醒

#### 4.2.2 遗忘曲线模型

**衰减公式**（Demo 阶段简化版）：

```plain&#x20;text
strength(t) = e^(-base_decay_rate × personal_sensitivity × t)


```

**复习节点**：

| 复习节点  | 距注入时间   | strength 阈值 | 提醒强度 |
| ----- | ------- | ----------- | ---- |
| 第 1 次 | 约 1 天后  | ≤ 0.61      | 轻度   |
| 第 2 次 | 约 3 天后  | ≤ 0.37      | 中度   |
| 第 3 次 | 约 7 天后  | ≤ 0.14      | 重要   |
| 第 4 次 | 约 14 天后 | ≤ 0.05      | 重要   |
| 第 5 次 | 约 30 天后 | ≤ 0.018     | 最终提醒 |

**推送阈值**：

* strength ≤ 0.3：触发"即将遗忘"提醒（L1）

* strength ≤ 0.15：触发强化提醒（L1+）

#### 4.2.3 L2 相似上下文触发

| 参数    | 值           | 说明                                |
| ----- | ----------- | --------------------------------- |
| 相似度阈值 |             | 与 context\_snapshot 或 tags 的语义相似度 |
| 触发时机  | 消息送达后 2 秒内  | 实时，悄悄展示                           |
| 防抖    | 24 小时/用户/记忆 | 同一记忆对同一用户最多一天一次                   |
| 展示形式  | 静默卡片        | 不 @ 用户，直接发到群聊                     |

#### 4.2.4 推送格式

**L1 衰减预警卡片**：

```plain&#x20;text
📌 你可能快忘了：

**决策**：项目数据库决定使用 MongoDB（存储用户数据）

💡 来源：群聊「技术方案讨论」| 4月20日
🔗 查看上下文：[点击查看]

———
[✅ 已复习] [🙋 已处理] [❌ 不再提醒]


```

**L2 相似上下文静默卡片**：

```plain&#x20;text
💡 关联提醒：

你之前提到过：
"这个接口要传 user_id 而不是 open_id"

来源：群聊「API 对接讨论」| 今天 14:32

[查看详情]


```

#### 4.2.5 业务规则

* BR-002-01：每日 L1 推送上限 3 条（按 strength 从低到高排序）

* BR-002-02：工作日推送时间窗口 09:00-19:00，批量合并

* BR-002-03：用户选择"不再提醒"后，该记忆进入"休眠"状态

* BR-002-04：30 天内未被复习的记忆自动转为"历史档案"，不再主动推送

* BR-002-05：周末压缩为每日一次合并推送

#### 4.2.6 验收标准（Given-When-Then）

* **Given** 一条记忆在 4 月 20 日被注入，**When** 4 月 21 日 strength 降至 ≤ 0.3，**Then** 触发 L1 复习推送

* **Given** 用户有 5 条到期记忆，**When** 推送时间到达，**Then** 只推送前 3 条（按 strength 从低到高排序）

* **Given** 群聊中出现与某记忆 context\_snapshot 相似度 > 0.75 的内容，**When** 消息送达后 2 秒内，**Then** 发送 L2 静默卡片到该群

* **Given** L2 推送后 24 小时内，**When** 同一用户再次触发相似内容，**Then** 不重复推送（防抖）

### 4.3 功能三：心流恢复推送（L0）

#### 4.3.1 功能概述

当用户被工作流打断后，通过快捷指令快速恢复之前的上下文。

#### 4.3.2 触发方式

| 触发方式    | 说明              |
| ------- | --------------- |
| 飞书机器人菜单 | 预设快捷指令"回到刚才的工作" |
| @bot 指令 | `@Mneme 回到刚才`   |

#### 4.3.3 推送内容

```plain&#x20;text
🔄 心流恢复：

你刚才在讨论：
"这个接口要传 user_id 而不是 open_id"

来源：群聊「API 对接讨论」| 15 分钟前

继续刚才的工作？[查看上下文]


```

#### 4.3.4 业务规则

* BR-003-01：L0 推送基于 context\_snapshot，即时触发，不定时

* BR-003-02：context\_snapshot 保留最近 30 分钟内的暂存记录

* BR-003-03：用户明确"开始新任务"后，清除暂存上下文

#### 4.3.5 验收标准（Given-When-Then）

* **Given** 用户之前提到"等下记得发周报"，**When** 用户 @Mneme 回到刚才，**Then** 返回"context\_snapshot"中包含"发周报"的记忆

* **Given** 用户点击"开始新任务"，**When** 系统处理，**Then** 清除该用户的暂存上下文

***

### 4.4 功能四：时序敏感记忆覆写

#### 4.4.1 功能概述

当同一主题的新记忆注入时，自动识别并处理与旧记忆的冲突，基于时间戳判断权威版本。

#### 4.4.2 冲突检测逻辑

```plain&#x20;text
新记忆注入 → 检测冲突（语义相似度 > 0.75）→ 时序判断 → 旧记忆标记 inactive


```

**冲突判断**：语义相似度 > 0.75 视为同主题冲突

#### 4.4.3 冲突类型

| 冲突类型  | 示例                    | 处理方式                    |
| ----- | --------------------- | ----------------------- |
| 负责人变更 | "A 负责" → "B 负责"       | 旧记忆标记为 superseded，新记忆生效 |
| 数值变更  | "截止 4/30" → "截止 5/15" | 同上                      |
| 决策反转  | "用方案A" → "改用方案B"      | 同上                      |

#### 4.4.4 业务规则

* BR-004-01：被覆写的旧记忆保留内容，仅标记 `active=false` 和 `superseded_by=new_memory_id`

* BR-004-02：用户可通过 @bot 查询"某主题的历史版本"

* BR-004-03：覆写操作记录到 memory\_logs

#### 4.4.5 验收标准（Given-When-Then）

* **Given** 记忆 A："周报发给 A"（4月1日），**When** 新记忆 B："周报发给 B"（4月15日）注入，**Then** 记忆 A 标记 active=false，记忆 B 为当前有效记忆

* **Given** 用户 @Mneme 查询"周报发给谁"，**When** 系统处理，**Then** 返回"目前周报发给 B"，并注明更新时间

* **Given** 用户 @Mneme 查询"周报的历史"，**When** 系统处理，**Then** 返回所有版本的记忆

***

### 4.5 功能五：被动查询（@bot 交互）

#### 4.5.1 功能概述

支持用户随时通过 @bot 查询记忆内容，或显式存储新记忆。

#### 4.5.2 scope 注入语法

| 场景      | 语法                | 存入范围           |
| ------- | ----------------- | -------------- |
| 群内 @机器人 | `@Mneme 记住 xxx`   | personal（个人记忆） |
| 群内 @机器人 | `@Mneme 大家记住 xxx` | group（群记忆）     |
| 私聊机器人   | （默认）              | personal（个人记忆） |

#### 4.5.3 支持的指令

| 指令                 | 示例                            | 功能            |
| ------------------ | ----------------------------- | ------------- |
| `@Mneme 查询 [关键词]`  | `@Mneme 查询 API 密钥`            | 检索相关记忆        |
| `@Mneme 记住 [内容]`   | `@Mneme 记住 下周发布会的 PPT 由 D 负责` | 存储个人记忆        |
| `@Mneme 大家记住 [内容]` | `@Mneme 大家记住 每周五发周报`          | 存储群记忆         |
| `@Mneme 覆盖 [新内容]`  | `@Mneme 覆盖 周报现在发给 C`          | 显式触发覆写        |
| `@Mneme 我的记忆`      | `@Mneme 我的记忆`                 | 查看个人 + 所在群的记忆 |
| `@Mneme 回到刚才`      | `@Mneme 回到刚才`                 | 触发 L0 心流恢复    |

#### 4.5.4 查询结果返回规则

* **个人视角**：同时返回 personal + 所在群的 group 记忆

* **群内视角**：默认只返回 group 记忆，除非用户显式查询个人备忘

* **结果数量**：按相关度排序，最多展示 5 条

* **隐私保护**：敏感信息（密码、密钥）脱敏显示为 \*\*\*

#### 4.5.5 业务规则

* BR-005-01：查询结果按相关度排序，展示前 5 条

* BR-005-02：查询结果包含"来源"信息，支持点击跳转原始消息

* BR-005-03：显式"记住"的内容置信度强制设为 1.0

#### 4.5.6 验收标准（Given-When-Then）

* **Given** 用户 @Mneme 查询"API 密钥"，**When** 记忆库中存在相关内容，**Then** 返回匹配的记忆列表

* **Given** 用户 @Mneme 查询"API 密钥"，**When** 不存在相关内容，**Then** 返回"未找到相关记忆，我可以帮你记住吗？"

* **Given** 用户 @Mneme 记住"下次会议改到周三"，**When** 系统处理，**Then** 成功存储并回复"已记住：下次会议改到周三 \[personal]"

* **Given** 用户 @Mneme 大家记住"每周五发周报"，**When** 系统处理，**Then** 成功存储并回复"已记住：每周五发周报 \[group]"

## 五、非功能需求

### 5.1 性能要求

| 指标      | 要求                  |
| ------- | ------------------- |
| 消息处理延迟  | < 2 秒（从收到消息到判定是否存储） |
| 查询响应时间  | < 1 秒（不含网络延迟）       |
| L2 推送触发 | 消息送达后 2 秒内决策        |
| 定时任务精度  | 误差 < 15 分钟          |
| 并发支持    | 同时处理 100 个群的消息      |

### 5.2 安全要求

| 要求   | 说明                        |
| ---- | ------------------------- |
| 数据隔离 | 群 A 的记忆不会出现在群 B 的查询中      |
| 权限控制 | 只有 bot 所在群的用户可以查询该群记忆     |
| 敏感信息 | 自动识别并脱敏（如密码、密钥显示为 \*\*\*） |
| 幂等处理 | 基于 event\_id 去重，飞书重推不重复处理 |

### 5.3 可靠性要求

| 要求    | 说明                  |
| ----- | ------------------- |
| 推送到达率 | ≥ 99%（基于飞书消息可靠性）    |
| 数据持久化 | PostgreSQL 存储，支持备份  |
| 故障恢复  | 定时任务中断后，恢复时补发未推送的记忆 |

### C.3 实体类型定义

* **细召回**：context\_snapshot 辅助实体关系推断

* 实体直接存入 tags，支持按类型筛选
